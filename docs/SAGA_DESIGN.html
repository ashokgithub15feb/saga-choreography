Movie Booking Saga: Choreography with Kafka

Three Spring Boot services book cinema seats without a distributed transaction. Each service commits its own local transaction and announces the result as an event. The next service reacts to that event. When a step fails, earlier steps are undone by compensating actions.

Spring Boot 3.5.7 Java 21 spring-kafka 3.3 Kafka Confluent Cloud MySQL database per service Swagger springdoc 2.8.9

Services

Booking service

  • Port 9191, MySQL booking_db
  • REST POST /booking-service/bookSeat
  • REST GET /booking-service/bookings/{id}
  • Owns the booking and its saga status
  • Outbox + relay, Idempotency-Key
  • Consumes seat-reserved-topic, payment-events

Seat inventory service

  • Port 9292, MySQL seat_inventory_db
  • Locks seats, reserves them, releases them
  • REST GET /seat-inventory-service/seats (read only)
  • Optimistic locking (@Version)
  • Lock expiry scheduler (saga timeout)
  • Consumes movie-booking-events, payment-events

Payment service

  • Port 9393, no database
  • Simulated gateway: amount > 2000 fails
  • Failure simulator (dev profile)
  • Pure Kafka read → process → write (exactly-once)
  • Consumes seat-reserved-topic

02Why a saga

A booking touches two databases (booking, seat inventory) and an external payment step. A single ACID transaction across them would need two-phase commit (XA). That's slow, holds locks across services, blocks when the coordinator dies, and Kafka doesn't take part in XA anyway. A saga splits the work into local transactions. Each local transaction publishes an event, and each step that can be undone has a compensating transaction.

Step (local transaction)ServiceCompensation
Create booking (PENDING)BookingMark booking FAILED
Lock seats (LOCKED + lockedUntil)Seat inventoryRelease seats (AVAILABLE)
Charge paymentPaymentRefund (only logged today, see gaps)
Reserve seats (RESERVED), confirm bookingSeat inventory, Booking(final step, the pivot)

Choreography vs orchestration

Choreography (this project)Orchestration
Who decides the next stepEach service reacts to events, with no central brainAn orchestrator sends commands and waits for replies
CouplingLoose: services only know topicsServices know the orchestrator's commands
Where saga state livesSpread out (booking status, seat status)In one place (the orchestrator's saga instance)
DebuggingHarder: you follow events across servicesEasier: one place shows the whole saga

Semantic lockSagas have no isolation: other transactions see intermediate states. The LOCKED seat status is a semantic lock, the standard countermeasure. It marks the seat as "in a saga, don't touch" until the saga finishes (RESERVED) or compensates (AVAILABLE).

03Flow A: happy path (booking confirmed)

The user books seats and everything succeeds. Dashed arrows are events, numbers give the order. Steps 4b, 6 and 7 are consumers reading the same event in different groups, so they run in parallel.

Every service ends in a final state: the booking is CONFIRMED, the seats are RESERVED, and the payment is captured.

04Flow B: payment failed (compensation)

Steps 1–4 of the happy path already ran, so the seats are LOCKED. Now the payment is declined. Solid yellow arrows are the compensation flow, like the "transaction failed" picture.

After compensation: the seats are AVAILABLE again, the booking is FAILED, and nothing is charged.

05Flow C: seats unavailable

Someone else already holds seat A1, or a seat number doesn't exist. The saga fails at the first step, before any money moves.

#What happens
1Same as the happy path: the booking is PENDING and the event goes through the outbox.
2handleBooking finds a seat that isn't AVAILABLE, or fewer seats than requested (an unknown seat number counts as unavailable). Nothing is changed.
3It publishes SeatReservedEvent(reserved=false, amount).
4Booking moves PENDING → FAILED.
4bPayment skips it (reserved=false).
Not the same as a poison message"Seat taken" is a valid business outcome, so it becomes an event. A BookingCreatedEvent with no bookingId, showId or seatIds is bad data. It throws PoisonMessageException and goes straight to movie-booking-events-dlt.

06Flow D: saga timeout (lock expiry)

Payment never answers. It might be down, or its input sits in the DLT after the retries ran out. Without a timeout, the seats would stay LOCKED forever.

#What happensCode
1Every seat.lock.sweep-interval (30s), the scheduler finds seats that are LOCKED with lockedUntil < now and groups them by booking. Each booking is released in its own transaction. The scheduler re-checks the rows first, because they may have been confirmed in the meantime. A failure for one booking is logged and retried on the next sweep, and doesn't stop the others.SeatLockExpiryScheduler, SeatInventoryService.releaseExpiredLock
2It publishes SeatReservedEvent(reserved=false). The Kafka send is synchronized with the database transaction and commits right after it.SeatReserveProducer
3Booking moves SEATS_LOCKED → FAILED.BookingService.moveBookingTo
4?Late payment race: if the payment success arrives after the expiry, confirmSeatsOnPaymentSuccess finds no LOCKED seats. Someone else may already hold them, so it does not take them back. It logs REFUND REQUIRED and publishes reserved=false. That's why CONFIRMED → FAILED is an allowed transition.SeatInventoryService.confirmSeatsOnPaymentSuccess
Two timeouts, one owner each
  • Seat inventory owns the SEATS_LOCKED timeout through seat.lock.ttl (5m).
  • Booking only fails bookings still PENDING after booking.pending-timeout (15m). In that case seat inventory never answered at all, for example because the BookingCreatedEvent went to the DLT.
  • Keep the booking timeout well above the seat lock TTL, so a slow but alive saga isn't failed by the wrong side.
Optimistic locking settles the raceThe scheduler and a payment-success update can touch the same seat rows at the same moment. @Version makes one of them fail and retry. The scheduler retries on its next sweep; the listener retries through the error handler.

7.1 Transactional outbox

Problem: the old bookSeats saved the booking and then called Kafka. If the DB committed and Kafka failed, the event was lost and the saga never started. If Kafka was down, every booking request failed. You can't make "write MySQL" and "write Kafka" atomic directly.

Solution: write the event into an outbox_event table in the same MySQL transaction as the booking. A separate relay publishes those rows to Kafka afterwards.

Failure pointResultWhy it's safe
DB transaction fails at step 2Neither the booking nor the event existsAtomic local transaction
Kafka down at step 4Rows stay sentAt = NULL and are retried every second. Bookings keep being accepted.No Kafka call in the request path
Crash between 4 and 5The row is published again on the next pollAt-least-once. Seat inventory's BOOKING_CREATED:<id> check absorbs the duplicate.
A row can't be rebuilt (corrupt JSON or class)Logged and skipped; it stays visible in the tableDoesn't block the rest of the batch

The relay rebuilds the event object (Class.forName(eventType)) before sending, so JsonSerializer adds the same __TypeId__ header that consumers expect. BookingEventProducer uses @Transactional(propagation = MANDATORY), so it can't write an outbox row outside a business transaction. Sent rows are deleted after outbox.retention (7 days).

7.2 Kafka transactions (exactly-once within Kafka)

Setting spring.kafka.producer.transaction-id-prefix makes the producer transactional. Spring Boot then creates a KafkaTransactionManager and attaches it to every listener container. For each record, the container:

  • Exactly-once covers Kafka → Kafka only. The consumed offset and the produced event commit atomically. MySQL isn't part of the Kafka transaction. Its commit (step 6) runs just before Kafka's (step 9); this is "best-effort one-phase commit". The gap between them is closed by idempotent consumers.
  • isolation-level: read-committed: consumers never see records from aborted or in-flight transactions. Without it, a consumer could act on an event that was later rolled back.
  • transaction-id-prefix: <svc>-tx-${random.uuid}: the prefix must be unique per running instance. Producer-only transactions (the outbox relay, the lock-expiry sender) would otherwise fence each other across instances. For listener transactions, spring-kafka uses EOS mode V2, which fences zombies through consumer group metadata.
  • payment-service has no database, so for it the whole hop really is exactly-once: read SeatReservedEvent → write BookingPaymentEvent → commit the offset, all in one transaction.
  • Two transaction managers exist in booking and seat inventory: @Primary JpaTransactionManager (used by plain @Transactional) and Boot's KafkaTransactionManager (used by the container).

7.3 Acknowledgment

  • spring.kafka.listener.ack-mode: manual and enable-auto-commit: false. Every listener takes an Acknowledgment and calls ack.acknowledge() as its last line, so only after successful processing.
  • If the listener throws, acknowledge() is never reached. The exception goes to the DefaultErrorHandler, which retries or sends to the DLT.
  • Inside a Kafka transaction the container sends the offset to the transaction itself when the listener returns normally (sendOffsetsToTransaction). So acknowledge() is effectively redundant here, but it keeps the code correct if transactions are ever switched off.
  • Interview angle: auto-commit commits on a timer, regardless of whether processing finished. A crash after the commit but before processing loses the message (at-most-once). Manual or transactional commit gives at-least-once or exactly-once.

7.4 Retry with backoff, poison messages and the DLT

One DefaultErrorHandler bean per service (config/KafkaConfig); Spring Boot plugs it into every listener container.

The DLT write and the offset commit happen in the same Kafka transaction as the failed listener call, so a record is never both "in the DLT" and "still pending".

ClassExamplesHandling
TransientDB down (CannotCreateTransactionException), timeouts, ObjectOptimisticLockingFailureException, PaymentServiceException (gateway timeout)Default: everything not listed as poison is retried. ExponentialBackOffWithMaxRetries(3): initial 1s, multiplier 2, max 10s. That's 4 attempts in total over about 7s, then the DLT.
PoisonPoisonMessageException (our validation), IllegalArgumentException, NullPointerException, plus spring-kafka defaults: DeserializationException, MessageConversionException, ConversionException, MethodArgumentResolutionException, NoSuchMethodException, ClassCastExceptionaddNotRetryableExceptions(...): no retry, straight to the DLT.
Unreadable bytesMalformed JSON, unknown typeErrorHandlingDeserializer wraps JsonDeserializer and turns the failure into a DeserializationException, which goes to the DLT. Without it, the consumer would fail on every poll, forever.

Failed-record lifecycle (RetryListener)

  • failedDelivery(record, ex, attempt): WARN with topic-partition@offset, key, attempt number and message.
  • recovered(record, ex): ERROR, "sent to <topic>-dlt".
  • recoveryFailed(record, original, failure): the DLT publish itself failed. The offset is not committed, so the record is redelivered and goes through the whole cycle again. Nothing is lost.

DLT records and the DLT consumer

DeadLetterPublishingRecoverer writes to <topic>-dlt, same partition, with headers: kafka_dlt-original-topic/-partition/-offset/-timestamp, kafka_dlt-original-consumer-group, kafka_dlt-exception-fqcn, -cause-fqcn, -message, -stacktrace.

Each service runs a DeadLetterListener (group ${spring.application.name}-dlt-group, auto.offset.reset=earliest). It reads the value as a String, because a DLT can hold JSON that never deserialized, and logs one ERROR line per record. DLTs shared by two consumer groups (seat-reserved-topic-dlt, payment-events-dlt) are filtered by the original-consumer-group header, so each service logs only its own failures. The listener never throws, so a DLT record can't fail again.

7.5 Idempotency

Kafka delivers at least once to our database code: the outbox can re-send, a Kafka commit can fail after a DB commit, and a rebalance can redeliver. Every consumer that changes the database is therefore idempotent.

Consumer side: idempotency table (processed_event in seat inventory, booking_processed_event in booking)

One row per handled event (eventKey as the primary key, processedAt). It's inserted in the same DB transaction as the business change, so "the work was done" and "the work is recorded as done" can never disagree.

ServiceEvent keyOn duplicate
Seat inventoryBOOKING_CREATED:<bookingId>Skip the DB work, re-publish the outcome derived from the DB (seats held by this booking → reserved=true, otherwise false)
Seat inventoryPAYMENT_FAILED:<bookingId>Re-publish reserved=false
Seat inventoryPAYMENT_COMPLETED:<bookingId>If the seats aren't RESERVED, re-publish reserved=false
BookingSEATS_LOCKED:, SEAT_RESERVATION_FAILED:, PAYMENT_COMPLETED:, PAYMENT_FAILED: + bookingIdIgnore. The state machine would reject a repeated transition anyway.
Paymentnone (no DB)Kafka EOS makes read → write atomic. A real gateway would also need bookingId as the gateway's idempotency key.
One idempotency table per serviceSeat inventory uses processed_event; booking uses booking_processed_event. Both services used to share the javatechie schema, and both handle payment events under the same keys (PAYMENT_COMPLETED:<id>). With a shared table, whichever service went second saw the other one's row as "already processed" and skipped its own work: the booking stayed SEATS_LOCKED while its seats were RESERVED. Fixed by giving each service its own database (booking_db, seat_inventory_db, migration in docs/db/split-database-per-service.sql), plus distinct table names.
Why re-publish instead of just skipping?The dangerous duplicate is the one in the step 6–9 gap of 7.2: the DB committed, but the Kafka transaction (with the outgoing event) aborted. If the consumer simply skipped the redelivered record, the next event would never be sent and the saga would stall. Re-publishing is safe because every downstream consumer is idempotent too.

7.6 Concurrency: no double booking

Two bookings for seat A1 have different keys, so they can sit on different partitions and be processed by different threads or instances at the same moment. Both would read A1 as AVAILABLE. SeatInventory has @Version, so updates are conditional:

  • The processed_event insert of thread 2 is rolled back with the rest, so the retry is a clean first attempt.
  • Optimistic or pessimistic? Conflicts on the same seat are rare, and optimistic locking holds no DB locks while the service works. Pessimistic locking (SELECT … FOR UPDATE) blocks the second thread instead of failing it. That's better under heavy contention (a hot premiere), at the cost of lock waits and deadlock risk if seats are locked in different orders.
  • Booking has @Version too. Its status is updated from two topics, and so from two threads (seat-reserved and payment-events); without a version check one update could overwrite the other.

7.6.1 How @Version implements optimistic locking

Definition

Optimistic lockingA concurrency-control strategy that assumes conflicts are rare. Reading a row takes no lock. When the transaction writes the row back, the database checks that nobody else changed it since it was read. If someone did, the write is rejected and the caller must re-read and retry. It detects conflicts after the fact instead of preventing them up front.
Pessimistic lockingThe opposite approach: assume conflicts are likely and lock the row when reading (SELECT … FOR UPDATE). Other transactions that want the row wait until the lock is released, so a conflict can't happen, at the cost of waiting and possible deadlocks.

@Version (jakarta.persistence.Version) is the JPA way to switch on optimistic locking for an entity. It marks one numeric field (or a timestamp) as the row's version counter. Hibernate then manages it automatically: it's read with the row, compared on every update, and incremented on every successful update. Your code never sets it.

// seat-inventory-service: entity/SeatInventory.java
@Version
@Column(columnDefinition = "BIGINT NOT NULL DEFAULT 0")   // DEFAULT 0 so ddl-auto could add it to existing rows
private Long version;

What Hibernate does, step by step

#StepSQL / effect
1Read: the entity is loaded and its current version is remembered in the persistence contextSELECT id, status, current_booking_id, …, version FROM seat_inventory WHERE show_id=? AND seat_number IN (?) → version = 7
2Change in memory: plain setters, no SQL yetseat.setStatus(LOCKED); seat.setCurrentBookingId(id);
3Flush / commit: the UPDATE carries the old version in its WHERE clause and sets the new oneUPDATE seat_inventory SET status='LOCKED', current_booking_id=?, locked_until=?, version=8 WHERE id=1 AND version=7
4aRows updated = 1: nobody changed the row in betweenSuccess; the row is now version 8
4bRows updated = 0: another transaction already moved the row to version 8, so WHERE version=7 matches nothingHibernate StaleObjectStateException → JPA OptimisticLockException → Spring ObjectOptimisticLockingFailureException; the whole transaction rolls back

The check and the write are one atomic SQL statement: UPDATE … WHERE version = ?. The database's own row locking during that single statement guarantees that only one of two concurrent updates can match the old version. There is no window between "check" and "write".

Pitfalls

  • NULL versions: rows created before the column existed would have version = NULL, and WHERE version = NULL never matches. Hence NOT NULL DEFAULT 0 on the column.
  • Bulk and manual updates skip the check: a JPQL/native UPDATE … WHERE … or a hand-written SQL fix doesn't touch the version, so a transaction that read the row before could still overwrite it. Bump it yourself: UPDATE seat_inventory SET status='AVAILABLE', version = version + 1 WHERE ….
  • Retry with fresh data: retrying with the same stale entity fails again. The retry must run in a new transaction that re-reads the row, which the Kafka redelivery here does by design.
  • Only rows you write are checked: if a decision depends on a row you only read (and don't update), a concurrent change to it isn't detected (write skew). Use LockModeType.OPTIMISTIC_FORCE_INCREMENT or a pessimistic lock on that row. Here every seat the decision depends on is also updated, so all are checked.
  • Don't expect a catch inside the method: the failure usually surfaces at flush/commit, after your method body has returned. Handle it outside the @Transactional method (here: the Kafka error handler or the scheduler loop).
  • Across HTTP: to protect a "read, then edit in a form, then save" flow, send the version to the client (e.g. as an ETag) and require it back (If-Match), answering 412 Precondition Failed when it no longer matches.

7.6.2 Pessimistic locking (the alternative)

This project uses optimistic locking. This section shows how the same seat booking would work with pessimistic locking, and when you would switch.

Definition

Pessimistic lockingA concurrency-control strategy that assumes conflicts are likely. A transaction locks the rows when it reads them (SELECT … FOR UPDATE) and holds the locks until it commits or rolls back. Any other transaction that wants to lock or change those rows waits. Conflicts are prevented up front rather than detected at write time, so the second transaction never works on stale data and never needs a "conflict" retry.

JPA lock modes and the SQL they produce (MySQL / InnoDB)

JPA LockModeTypeMySQL SQLEffect
PESSIMISTIC_WRITESELECT … FOR UPDATEExclusive row lock: others can't lock or update the row until commit (plain non-locking reads still see the last committed version)
PESSIMISTIC_READSELECT … FOR SHAREShared lock: others may also share-lock it, but nobody can update it until all share locks are released
PESSIMISTIC_FORCE_INCREMENTFOR UPDATE + version bumpExclusive lock and increments @Version, even if the row isn't otherwise changed
lock-timeout hint 0… FOR UPDATE NOWAITFail immediately instead of waiting when the row is already locked
lock-timeout hint -2… FOR UPDATE SKIP LOCKEDSilently skip rows other transactions have locked (great for work queues, e.g. the outbox relay)

The seat booking with pessimistic locking

// SeatInventoryRepository: lock exactly the requested seats, in a fixed order (ORDER BY id) to avoid deadlocks
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select s from SeatInventory s where s.showId = :showId and s.seatNumber in :seats order by s.id")
List<SeatInventory> lockSeats(@Param("showId") String showId, @Param("seats") List<String> seats);

// SeatInventoryService.handleBooking: must run inside @Transactional, because the locks live until commit
List<SeatInventory> seats = seatInventoryRepository.lockSeats(event.showId(), event.seatIds());
// SQL: SELECT … FROM seat_inventory WHERE show_id=? AND seat_number IN (?, ?) ORDER BY id FOR UPDATE
boolean allAvailable = seats.size() == event.seatIds().size()
        && seats.stream().allMatch(s -> s.getStatus() == SeatStatus.AVAILABLE);
// … same LOCKED / reserved=true|false logic as today; COMMIT releases the row locks

The only change is the query used to read the seats. The business logic stays the same, and @Version can stay on the entity as a safety net.

Compare with the optimistic timeline in 7.6: there, thread 2 runs ahead, fails at commit, and has to be retried. Here it simply waits and then decides correctly the first time.

Timeouts and deadlocks

  • Lock wait timeout: a waiting transaction gives up after innodb_lock_wait_timeout (MySQL default 50s; set it lower per session, e.g. 3–5s, for request paths). On MySQL, Hibernate only maps the JPA lock-timeout hint values 0 (NOWAIT) and -2 (SKIP LOCKED); other values are ignored, so the timeout comes from the database setting.
  • Deadlock: T1 locks A1 then waits for A2, while T2 locked A2 and waits for A1. InnoDB detects the cycle and rolls back one transaction (MySQL error 1213). Prevent it by always locking rows in the same order, hence ORDER BY id in the query above.
  • Both are transient: Spring raises a PessimisticLockingFailureException (e.g. CannotAcquireLockException). It isn't in the non-retryable list, so the Kafka DefaultErrorHandler retries it with backoff, the same path as an optimistic conflict.
  • Keep lock-holding transactions short: never make HTTP calls or wait for slow work while holding row locks. Every waiting transaction also holds a DB connection.

MySQL / InnoDB traps

  • Index the lookup: InnoDB locks every row it scans, not just the rows it returns. seat_inventory has no index on (show_id, seat_number), so FOR UPDATE would scan and lock the whole table, serialising all bookings. Add UNIQUE(show_id, seat_number) first. It's also the natural business key.
  • Gap / next-key locks: under the default REPEATABLE READ isolation, range or non-unique lookups also lock the gaps between rows to block inserts. A unique-index equality lookup avoids them.
  • Plain reads don't wait: an ordinary SELECT (no FOR UPDATE) reads the last committed snapshot and is never blocked. Only locking reads and writes queue up.

When to switch from optimistic to pessimistic

The bug this fixed (a real incident in this project)

Migration

  • Why it matters: one owner per table lets a service change its schema, scale its database or pick a different store without coordinating with anyone. A shared database couples services at the data level, the coupling microservices are meant to remove.
  • Cost: no cross-service joins or ACID transactions. That's exactly why this project uses a saga, events and idempotent consumers.
  • Production: a separate MySQL user per service with grants on its own database only (commented-out example at the end of the script), so one service can't reach another's tables even by mistake.

11Interview questions (with answers from this project)

Saga fundamentals
What is the Saga pattern and why not use a distributed (2PC/XA) transaction?

A saga is a sequence of local transactions, one per service. Each one publishes an event or message that triggers the next. When a step fails, compensating transactions undo the earlier steps.

Why not 2PC/XA:

  • Locks are held across services for the whole protocol, which hurts throughput.
  • The coordinator is a single point of failure: participants block "in doubt" if it dies.
  • Kafka and most cloud databases don't support XA.
  • Services become tightly coupled in availability: all must be up to commit.

The trade-off: a saga gives eventual consistency and no isolation.

Choreography vs orchestration: which did you choose and when would you switch?

Choreography: three services and a short linear flow, so events are enough and there's no extra component to run.

I'd switch to an orchestrator (Temporal, Camunda, or a saga service of our own) when:

  • the flow grows branches, parallel steps or human approval;
  • we need one place to see "where is booking X";
  • event chains start to form cycles, or nobody owns the end-to-end flow.
What is a compensating transaction? What are its rules?

A compensating transaction is a business-level undo, not a database rollback. Here: release the seats (LOCKED → AVAILABLE) and mark the booking FAILED; for payment it would be a refund.

Rules:

  • It must be idempotent, because it can be delivered twice.
  • It must be retryable until it succeeds. A compensation can't be allowed to fail permanently, so give it retries, then a DLT and alerting.
  • It should be commutative where possible, since it may arrive before or after other events.
  • Some actions can't be compensated (an email already sent). Put those after the pivot transaction.
Sagas have no isolation. What anomalies can occur and how do you counter them?

Anomalies:

  • Lost updates: two sagas overwrite each other.
  • Dirty reads: reading data from a saga that later compensates.
  • Fuzzy reads: the same data reads differently within one saga.

Countermeasures used here:

  • Semantic lock: the LOCKED seat status means "in a saga, don't touch".
  • Version check: @Version on seats and bookings.
  • Pivot-based ordering: irreversible actions come after the pivot.

Others: commutative updates, re-reading values before acting, and the "by value" strategy (choosing concurrency control per request based on business risk).

What if a saga step never replies?

Every saga needs timeouts. Here:

  • lockedUntil with a scheduler in seat inventory releases the seats after 5m and tells booking.
  • Booking fails anything still PENDING after 15m.
  • Each timeout has exactly one owner, so the two sides don't race.
  • The late-reply case is handled explicitly: a payment that succeeds after the lock expired gets a refund, not a stolen seat.
Messaging guarantees
At-most-once, at-least-once, exactly-once: what does each hop give you here?
  • REST → Kafka: outbox gives at-least-once, never lost.
  • Kafka → payment → Kafka: exactly-once (Kafka transactions, no DB).
  • Kafka → seat or booking DB: at-least-once delivery plus idempotent processing, which is effectively once.

Exactly-once across Kafka and a database requires idempotency or the outbox. Kafka transactions alone can't do it.

You enabled Kafka exactly-once. Why do you still need idempotent consumers?

EOS makes consume-offset and produce atomic within Kafka. The MySQL commit is a separate transaction. If MySQL commits and the Kafka commit then fails (crash, rebalance, fencing), the record is redelivered, and without idempotency the seats would be locked twice.

The outbox relay is also at-least-once by design.

Outbox vs Kafka transactions vs "send after commit": when to use which?
  • Send after commit: loses the event if the process dies in between. Not acceptable.
  • Kafka transactions: ideal for consume → produce flows (payment-service) and for the listener's own output.
  • Outbox: for "DB change + event" started by a non-Kafka trigger such as a REST call. The DB is the single source of truth, and a relay (polling here; Debezium CDC in high-volume systems) publishes it.

Both are used here: the outbox in booking, Kafka transactions everywhere.

How is ordering guaranteed?

Kafka orders records only within a partition. All events are keyed by bookingId, so one booking's events on one topic are in order.

Across topics there's no ordering: booking can see the payment result before "seats locked". The state machine accepts forward moves only and tolerates this.

Retry topics (non-blocking retries) would break per-key order. That's one reason this project uses blocking retries.

What does read_committed do, and what breaks without it?

With read_committed, consumers skip records from aborted transactions and wait for open transactions (they only read up to the "last stable offset"). With the default read_uncommitted, a consumer could act on an event whose transaction later aborted, for example lock seats for a booking event that "never happened".

What is transactional.id and zombie fencing?

A transactional producer registers a transactional.id. The broker bumps an epoch each time it's initialized, and any older producer instance with the same id (a "zombie", e.g. after a long GC pause) is fenced: its writes and commits are rejected.

With EOS V2 (Kafka 2.5+), listener transactions are fenced using consumer group metadata, so one producer per consumer thread is enough. The prefix gets a random suffix per instance so producer-only transactions (outbox relay, schedulers) on different instances don't fence each other.

Manual ack vs auto-commit? What does acknowledge() do inside a transaction?
  • Auto-commit commits on a timer, regardless of processing, so a crash can lose or duplicate messages.
  • Manual ack commits after success.
  • With a KafkaTransactionManager the container adds the offset to the transaction when the listener returns normally, so the commit is part of the same atomic unit as the produced events. acknowledge() is then informational, but keeps the code correct without transactions.
Errors, retries, DLT
How do you separate transient failures from poison messages?
  • Default: retry everything; most unknown errors are infrastructure problems.
  • Not retryable: exceptions that can never succeed on retry: our PoisonMessageException (validation), IllegalArgumentException, NullPointerException, and deserialization or conversion errors (spring-kafka defaults).
  • Business failures (payment declined, seat taken) are events, not exceptions, so they never reach the error handler.
Blocking vs non-blocking retries: trade-offs?
  • Blocking (DefaultErrorHandler + backoff, used here): simple, keeps per-partition order, but the partition is stuck during the backoff (head-of-line blocking, about 7s at most here). Keep the total backoff well below max.poll.interval.ms and the transaction timeout.
  • Non-blocking (@RetryableTopic): failed records move to -retry-1s, -retry-2s topics, so the main partition keeps flowing. Order is lost, and there are more topics to run. Choose it when throughput matters more than per-key order.
What's a poison pill and why does ErrorHandlingDeserializer matter?

A record that can never be processed. If it can't even be deserialized, the failure happens inside poll(), before any listener or error handler runs, so the consumer fails on the same offset forever. ErrorHandlingDeserializer catches it, passes a null value plus the exception header to the container, and the error handler sends the raw record to the DLT.

What's in a DLT record and how do you replay it safely?

The original key and value, plus headers: original topic, partition, offset and timestamp, the consumer group, and the exception class, cause, message and stack trace.

To replay:

  1. Fix the cause.
  2. Republish the value to the original topic (a small replay tool or endpoint).

It's safe because consumers are idempotent. A record that arrives after the saga timed out is rejected by the state machine (FAILED is terminal) or triggers the refund path.

What if publishing to the DLT fails?

RetryListener.recoveryFailed logs it. The recoverer threw, so the offset isn't committed and the record is redelivered and goes through the retry cycle again. Nothing is silently dropped.

Data integrity
How do you prevent double booking of a seat?

Optimistic locking with @Version (diagram 7.6). The loser gets ObjectOptimisticLockingFailureException, rolls back (including its idempotency row), is retried by the error handler, sees the seat LOCKED and publishes reserved=false. Alternatives: SELECT … FOR UPDATE (pessimistic), a unique constraint on (show, seat, active booking), or partitioning by showId so one consumer owns a show (serializes all of that show's bookings).

How do you implement an idempotent consumer?
  • A dedup table keyed by event identity (business key here; an event id is better), inserted in the same DB transaction as the business change.
  • On a duplicate, skip the DB work, but re-emit the outcome so a lost downstream event is recovered.
  • Make updates naturally idempotent where possible: state machines, "set status" instead of "increment".
  • Clean old rows up with a TTL.
What is optimistic locking and how does @Version implement it?

Optimistic locking takes no lock when reading. Instead it checks at write time that the row is unchanged, and rejects the write if not. JPA's @Version adds a version column that Hibernate puts into every update: UPDATE … SET …, version = 8 WHERE id = ? AND version = 7.

  • 1 row updated: success.
  • 0 rows updated: someone else changed the row first, so Hibernate throws OptimisticLockException (Spring: ObjectOptimisticLockingFailureException) and the transaction rolls back.
  • Here, the Kafka error handler retries the losing booking. It re-reads the seat, sees it LOCKED, and fails that booking.
  • Pessimistic locking (SELECT … FOR UPDATE) makes the second transaction wait instead. Choose it for heavy contention on the same rows.

Full walkthrough: 7.6.1.

When would you use pessimistic locking, and how in JPA?
  • When conflicts are frequent (many users fighting for the same rows), or when a conflict retry is expensive. Waiting is then cheaper than failing and retrying.
  • How: @Lock(LockModeType.PESSIMISTIC_WRITE) on a repository query, which produces SELECT … FOR UPDATE. It must run inside @Transactional, because the lock is held until commit.
  • Risks: lock waits (a timeout raises CannotAcquireLockException), deadlocks (always lock rows in the same order), and connection-pool exhaustion while transactions wait.
  • MySQL specifics: index the lookup, or InnoDB locks every row it scans. Use NOWAIT to fail fast, and SKIP LOCKED for work queues.

Full walkthrough: 7.6.2.

How do you make a POST idempotent?
  • The client sends an Idempotency-Key, stored with a unique constraint.
  • Same key + same body: return the stored result.
  • Same key + different body: 422.
  • Concurrent duplicates: the unique constraint decides the winner, and the loser gets 409 Conflict and retries with the same key (as the IETF Idempotency-Key draft recommends).
  • Keys should expire after a while (24h is common).
Why not use System.currentTimeMillis() or a short code as an ID?

Two requests in the same millisecond collide on the primary key, and IDs from different instances are not coordinated. Eight hex characters is only 2^32 values, so by the birthday paradox collisions become likely after about 65k bookings. Use DB sequences or identity columns for internal keys, UUIDs (or ULIDs/UUIDv7 for index locality) for public IDs, and enforce uniqueness with a constraint.

Why database per service? Did sharing one ever bite you?

Yes, in this project. Booking and seat inventory shared the javatechie schema and, through it, one processed_event table. Both consume payment-events and build the same idempotency key, PAYMENT_COMPLETED:<id>. Seat inventory inserted it first, so booking's duplicate check found that row and skipped the event. The seat ended up RESERVED while the booking stayed SEATS_LOCKED.

Database per service fixes this whole class of bug:

  • Each service owns its schema, so no hidden coupling through shared tables.
  • Each service can change, scale or replace its store on its own.
  • Per-service DB users enforce the boundary.

Trade-off: no joins or ACID transactions across services. That's why you need sagas, events, and data replicated through events (CQRS read models) for cross-service queries.

Lesson for idempotency: a dedup key must be unique within the consumer's own scope. Different consumers of the same event need separate stores, or a consumer prefix in the key.

How do you retry a failed HTTP call safely?
  • Classify the error. Retry only what can succeed later: 5xx, 408, 429, 409 ("in progress"), timeouts and connection errors. Never retry 400, 404 or 422, because the same request fails the same way.
  • Back off exponentially (1s, 2s, 4s here; add jitter in production) and cap the number of attempts (3 retries), so a struggling service isn't hammered.
  • Make the call idempotent. Reuse the same Idempotency-Key on every retry. If the first attempt actually succeeded but its response was lost, the retry returns that booking instead of creating a second one.
  • Don't drop what still fails. Park it in a DLT (booking-request-dlt) with everything needed to inspect or replay it, and alert on it.
  • In production: Resilience4j (Retry + CircuitBreaker) or Spring Retry rather than a hand-written loop.
How did you prove there's no double booking under concurrency?

With BookingLoadSimulator (section 15):

  • It releases 10–15 requests for the same 3 seats at the same instant: a CountDownLatch gate, with one virtual thread per user.
  • After the saga settles, it reads every booking's status and asserts that each seat has at most one CONFIRMED booking.
  • What makes this hold is optimistic locking on seat_inventory (@Version) plus the saga. The loser of a race is retried by the Kafka error handler, sees the seat LOCKED, and its booking fails.
  • In a real test suite the same idea runs as a Testcontainers test, with Awaitility for the async assertion.
Operations & design
How do you handle errors in a Spring REST API?
  • Keep controllers free of try/catch. Use one @RestControllerAdvice with an @ExceptionHandler per exception type.
  • Extend ResponseEntityExceptionHandler so Spring MVC's own errors (missing header, validation, unreadable body) get consistent 4xx responses for free.
  • Return RFC 9457 ProblemDetail (type, title, status, detail, instance).
  • Map domain exceptions to precise statuses: 422 (key reused), 409 (concurrent duplicate).
  • Have a final Exception handler that logs the stack trace and returns a generic 500, so internals never leak to the client.
How do you scale consumers?
  • Parallelism is capped by the partition count: 3 here, so at most 3 consumers per group are active.
  • Set spring.kafka.listener.concurrency (default 1) and/or run more instances.
  • Rebalances reassign partitions. Uncommitted transactions abort, and idempotency covers the replay.
  • Keep processing time plus backoff below max.poll.interval.ms.
How would you observe and debug a saga in production?
  • Correlation or trace id propagated in Kafka headers (Micrometer Tracing + OpenTelemetry).
  • Saga state queryable per booking.
  • Metrics: consumer lag, retry count, DLT rate, outbox backlog (unsent rows, oldest age), stuck LOCKED seats.
  • Alerts on DLT > 0 and an outbox age above a threshold.
  • Structured logs keyed by bookingId.
How do you evolve event schemas without breaking consumers?

Add only optional fields, never rename or remove fields in place, and version events (v field or type). Better: Avro or Protobuf with a Schema Registry and BACKWARD/FORWARD compatibility checks in CI. Also restrict spring.json.trusted.packages: * plus type headers lets a producer choose which class you deserialize into.

How would you test this?

Testcontainers (Kafka + MySQL) or @EmbeddedKafka. One test per flow: happy path, payment declined, seats taken, poison message lands in the DLT, transient failure recovers, duplicate delivery doesn't double-apply, concurrent bookings of one seat, lock expiry, outbox re-send after a crash, Idempotency-Key replay and 422. Use Awaitility for async assertions. Add contract tests for event schemas.

Several instances run the schedulers and the outbox relay. Is that a problem?

It's correct but wasteful: duplicate sends and sweeps are absorbed by idempotency, re-checks and @Version. To avoid it, use ShedLock (one instance runs each job), SELECT … FOR UPDATE SKIP LOCKED in the relay so instances split the rows, or replace polling with Debezium CDC.

15Concurrency demo: BookingLoadSimulator

A scheduler in booking-service (simulator/BookingLoadSimulator) that stages a rush: 10–15 people trying to book the same few seats at the same moment. Requests are built from real data: show and seats come from seat-inventory's API, while users, amounts and Idempotency-Keys are random. Some users get errors on purpose, which are retried 3 times and then sent to a DLT. The result proves the system never confirms one seat twice.

#What happens
1Trigger: @Scheduled, the first rush 20s after startup and then every 5 minutes, automatically while booking.simulator.enabled=true. It fetches AVAILABLE seats from seat-inventory over HTTP. It doesn't read seat_inventory_db, which belongs to another service (7.8).
2It picks one random show and 3 of its seats (the contested pool). For each of 10–15 people it builds a request with a random name (John-3), one contested seat, a random amount of 300–2500 (so about 1 in 5 payments fail), a new Idempotency-Key, and a chaos mode.
3Every person waits on a CountDownLatch on their own virtual thread. countDown() releases all POST /bookSeat calls at the same instant, so several requests really race for the same seat.
4Errors and retry: a retryable error (5xx, 408, 409, 429, I/O) is retried up to 3 times after 1s, 2s and 4s, always with the same Idempotency-Key. A non-retryable one (400, 404, 422) isn't retried.
5Gave up: a FailedBookingRequest (user, show, seats, amount, Idempotency-Key, attempts, last error, reason, chaos, time) is published to booking-request-dlt in its own Kafka transaction, keyed by the Idempotency-Key.
6DeadLetterListener.consumeFailedBookingRequest logs every record of booking-request-dlt.
7After settle-time (45s) it calls GET /bookings/{id} for every booking and logs a RESULT table (user, seat, amount, chaos, attempts, final status) with totals. For each seat it checks that at most one person got CONFIRMED; a second winner would be logged as DOUBLE BOOKING!.
